# ADR-0002: Schema migrations, evidence invariants as constraints, and the SQLite import

- **Status:** Proposed
- **Date:** 2026-11-23
- **Related:** ADR-0001, ADR-0005, ADR-0006, ADR-0008, D-012, D-021

## Context

- `storage/db/schema.py` runs additive, idempotent migrations (tracked in
  `schema_migrations`) every time a `Database` is constructed (P-242, FINDINGS §7).
- **Events are not really append-only:** the docstring promises "no UPDATE or DELETE
  ever", yet `events` has mutable `processed_at`, `ranked_at` and `notified_at` columns.
- `evidence.observation_ids` is JSON text, so evidence has no real foreign keys.
- **Attribution is decided in storage** (`_evidence_attribution_status`,
  `storage/db/evidence.py:103-137`), and non-research sources are auto-attached
  (FINDINGS §4).
- **Source independence exists only in batch discovery** (`origin_key`,
  `mark_source_independence`, `batch_discovery/engine.py:481,609`), yet Inbox rows claim
  "N independent origins" (FINDINGS §6).
- State lives in unlocked JSON files shared across processes (FINDINGS §10, P-272–P-275).
- **Owner invariants:** immutable observations; provenance everywhere; unbound same-name
  evidence never strengthens an entity; several tools hitting one source never raise
  confidence; JSON canonical, Markdown compiled; erasure and opt-out (GDPR, DPDP).

## Decision

1. **Alembic** (MIT; 1.16+, verify) owns the schema, in
   `backend/venture_intelligence/storage/migrations/`.
   - Revision 0001 is the Postgres baseline: the final SQLite shape plus the constraints
     below.
   - Production migrations are forward-only and use expand/contract for breaking changes.
   - Triggers, policies and grants are hand-written `op.execute` SQL, never autogenerated.
   - The application never runs DDL. `vi db upgrade` and the compose `migrate` service run
     migrations, and readiness fails unless the database is at head (ADR-0004).
   - CI runs `alembic upgrade head` on an empty database, then `alembic check` to catch
     drift.
2. **Roles:**
   - `vi_owner` owns objects and runs migrations.
   - `vi_app` is the runtime role: not an owner, and `NOBYPASSRLS`.
   - `vi_erasure` is used only by the erasure and erasure-replay functions.
   - `vi_readonly` runs backups.
3. **Two tiers of write protection.** For both tiers, `vi_app` loses `UPDATE`, `DELETE`
   and `TRUNCATE`, and row-level `BEFORE UPDATE OR DELETE` triggers plus a
   `BEFORE TRUNCATE` trigger raise `vi_append_only` for every role, including the owner.
   - **Tier 1, the evidence record:** `events`, `observations`, `observation_bindings`,
     `batch_discovery_observations`, `candidate_rejections`, `model_runs`,
     `people_query_audit`, `erasure_log` and `maintenance_log`. Only erasure may change
     these rows, except that the retention purge may delete expired
     `people_query_audit` rows.
   - **Tier 2, append-only histories:** `crm_events`, the recommendation and alert
     lifecycle tables, and `features`. Rows are never updated. They may be deleted only
     through the reconcile path.

   Other derived projections (signals, rankings, graph, evidence, entities) stay
   ordinary tables that the pipeline rebuilds. Pipeline progress moves out of `events`
   into `event_processing(event_id, stage, completed_at)`. A view still exposes
   `processed_at`, `ranked_at` and `notified_at`, so `/api/events` (P-009) is unchanged.
4. **Exactly three audited maintenance paths (D-012).** Each is a `SECURITY DEFINER`
   function that sets a transaction-local flag the triggers honour; no other function or
   role can set it. Erasure has two entry points that share one tombstoning routine.
   - **Erasure:** `vi_erase_subject(subject_ref, request_id)`, in one transaction:
     - replaces personal payload fields in tier-1 and tier-2 rows with a tombstone;
     - deletes derived rows;
     - writes `erasure_log` with the request id, the subject key hash and the erased row
       ids;
     - adds the subject key hash to `subject_suppressions`.

     The subject key hash is a hash of the normalised subject identifier. It is the only
     subject reference kept after erasure, and `subject_suppressions` is keyed by it.
     The identity gate (P-227) hashes each candidate's subject identifier the same way
     and checks `subject_suppressions` before accepting new observations, which
     implements opt-out. Row ids, the source host and timestamps survive as content-free
     tombstones, so audit counts stay coherent (owner decision, D-021).

     **Replay mode:** `vi_replay_erasure(subject_key_hash, row_ids, request_id)` applies
     the same tombstoning to the listed row ids, deletes their derived rows, writes
     `erasure_log` and adds the hash to `subject_suppressions`. It needs no
     `subject_ref`, is idempotent, and only the owner role (restore, ADR-0005) and the
     `vi_erasure` role (the erasure service's retry job) may execute it; `vi_app` cannot.

     **Erasure ledger outside the database.** `erasure_log` lives in the dump, so a
     restore would lose every erasure made after the backup. The erasure service in the
     service layer (ADR-0007), which every caller including `vi admin erase-subject` goes
     through, therefore also writes a two-phase, content-free record to an append-only
     JSONL ledger at `ERASURE_LEDGER_PATH`. The ledger sits on a separate volume, is
     excluded from the database dump and is backed up alongside it (ADR-0005).
     - **Intent:** before the transaction commits, the service appends and fsyncs an
       intent line (request id, subject key hash, erased row ids, timestamp, actor). If
       the append fails, the erasure rolls back.
     - **Commit marker:** after the transaction commits, it appends a commit line for
       that request id. The marker is for reporting only; nothing reads it to decide
       whether to erase.

     There are no abort lines and no resolution step: an intent is never cancelled. A
     periodic worker job (ADR-0003), connecting as `vi_erasure`, calls `vi_replay_erasure` for every intent whose
     request id has no `erasure_log` row, and restore replays every intent in the
     ledger, marked or not (ADR-0005). Row-id erasure is idempotent, so re-applying an
     erasure whose original transaction rolled back is the intended outcome: the subject
     asked to be erased, so the erasure is retried until it succeeds. Erased data
     therefore cannot come back through a restore, whatever crashed and whenever.
   - **Reconcile** (P-103, P-243) may delete tier-2 rows only. It first copies each row
     into `reconcile_archive(run_id, table, row)`, so polluted CRM and lifecycle history is
     recoverable. Today it is destroyed (`storage/cleanup.py:436-462`). Reconcile never
     touches tier 1. Its in-place re-pointing of observations and evidence
     (`storage/cleanup.py:124-175`) becomes appended bindings plus rebuilt derived rows.
   - **Retention purge:** `vi_purge_people_audit()` deletes `people_query_audit` rows
     older than the retention period (12 months by default, set by
     `PEOPLE_AUDIT_RETENTION_MONTHS`; ADR-0006, D-021) and appends one
     `maintenance_log` row per run (cutoff, rows deleted, time, actor). It takes no
     arguments: it reads the period from an owner-only settings row, so `vi_app` can run
     it from a daily job (ADR-0003) but cannot shorten retention. `vi db upgrade`, run
     under the owner role by the `migrate` service (item 1, ADR-0005), writes
     `PEOPLE_AUDIT_RETENTION_MONTHS` into that row on every run; `vi_app` may read the
     row but has no write access to it. The purge touches no other table.
5. **Provenance is `NOT NULL`.**
   - `events.source`, `source_url` (`CHECK` non-empty, http or https), `observed_at` and
     `ingested_at` are required.
   - `observations.event_id` is a foreign key to `events`.
   - Lineage that feeds scoring uses join tables with foreign keys (`evidence_support`,
     `feature_inputs`); other lineage arrays carry `CHECK (jsonb_array_length(x) > 0)`.
   - Every confidence column has `CHECK (confidence BETWEEN 0 AND 1)`.
   - Every timestamp is `timestamptz`.
6. **Unbound evidence cannot strengthen an entity.** Attribution leaves storage and
   becomes data in the append-only table
   `observation_bindings(binding_id, observation_id, entity_id, status, reason_code NOT
   NULL, decided_by, decision_id)`.
   - `status` is attached, unbound or contradictory. The latest binding wins.
   - Support reaches scoring only through
     `evidence_support(evidence_id, binding_id, entity_id, status, origin_key)`.
   - That table has `CHECK (status = 'attached')` and composite foreign keys to the
     binding and the observation. The database therefore rejects support from an unbound
     or contradictory binding, or from a binding for another entity.
   - Tests, not constraints, enforce that a superseding binding triggers recomputation.
7. **One source raises confidence at most once.**
   - Every observation stores `origin_key NOT NULL`, a digest of the canonical origin,
     and `derivative_of`. `mark_source_independence` becomes the single implementation.
   - `evidence_support` is `UNIQUE (evidence_id, origin_key)`: two tools fetching one page
     yield two observations but one support row.
   - The confidence calculation stays deterministic Python. A Hypothesis (MPL-2.0)
     property test asserts that duplicating same-origin observations never changes it.
8. **JSON is canonical.**
   - Canonical records are `jsonb`. Markdown pages (P-256) are build outputs; no column
     holds authoritative Markdown.
   - The JSON state files become tables with row locks: `email_settings`,
     `source_settings`, `source_state`, `scheduler_state` and the delivery outbox
     (ADR-0003). This ends the lost-update race (FINDINGS §5 cause 9).

**SQLite import:** `vi db import-sqlite --from PATH [--dry-run] [--resume]` runs these
steps:

1. Checkpoint the WAL and copy the file. The original is never written.
2. Run the frozen legacy additive migrations on the copy, so any historical version
   (for example pre-M5 or M8) reaches the final SQLite shape.
3. Require an empty target at Alembic head. `--resume` instead uses `ON CONFLICT DO
   NOTHING` on primary keys, which makes reruns idempotent.
4. Copy tables in foreign-key order with psycopg `COPY`, converting as it goes:
   - text timestamps become `timestamptz`;
   - JSON text becomes `jsonb`;
   - `observation_ids` arrays become join rows;
   - `origin_key` and bindings are derived with the shared functions.

   Legacy auto-attached evidence keeps `attached` with
   `reason_code = 'legacy_auto_attach'`, so the S2 identity review can re-examine it.
5. Write rows that violate constraints to `import_quarantine(table, pk, reason, row)`.
   Nothing is silently dropped.
6. Import the four JSON state files and the delivery log.
7. Report per-table source, imported and quarantined counts plus verification digests,
   in TOON or JSON. Exit 0 only when counts reconcile and digests match.

## Alternatives considered

- **Port the in-house runner to Postgres:** no new dependency, but no drift check and no
  downgrades, and it keeps DDL at startup. Rejected.
- **Sqitch (MIT, Perl) or Flyway Community (Apache-2.0, JVM):** good plain-SQL migrations,
  but each adds a second runtime to the image and to CI. Rejected.
- **Invariants only in Python (status quo):** flexible, but every new path (MCP, scripts,
  ad-hoc SQL) must remember the rules, and FINDINGS §4 shows the rule has already drifted
  into storage. Python checks stay as the first line of defence, because they give clearer
  errors.
- **An event-sourcing framework (for example `eventsourcing`, BSD-3):** a strong
  append-only model, but it would mean rewriting the pipeline. Rejected.

## Consequences

- **Old pollution surfaces.** New foreign keys and `CHECK`s expose existing polluted rows.
  Quarantine makes them visible, and reconcile (P-103, P-243) remains the repair tool.
  Reconcile now runs through the archived maintenance path and can no longer rewrite
  tier-1 rows.
- **Erasure, reconcile and the retention purge are documented, audited exceptions** to
  immutability.
- **Migration steps:** (1) the baseline migration and roles; (2) `event_processing` and
  the compatibility view; (3) bindings, support and `origin_key`, with attribution moved
  out of storage; (4) append-only triggers; (5) JSON state files into tables; (6) the
  importer with fixtures; (7) the erasure function and ledger, and the retention purge
  (with ADR-0006).
- **Parity risks:**
  - `db fresh` (P-102) now needs the owner role.
  - Imported legacy attribution is preserved as-is, not silently "fixed".
  - Reconcile's report (`derived_rows` per table) must stay the same, and now also
    names the archive run id.

## How parity is verified

- The migration tests behind P-242 (`test_previous_schema_is_migrated_additively`,
  `test_m8_migration_is_additive_and_idempotent`) become importer tests. Every historical
  SQLite fixture imports with reconciled counts, and a second run is a no-op.
- The demo dataset round-trips. So does an owner-run copy of a real install, for which
  only counts are reported. Replay digests, the rankings read model and the knowledge JSON
  are identical to the SQLite build.
- Constraint tests:
  - `UPDATE`, `DELETE` and `TRUNCATE` fail on every tier-1 and tier-2 table, for both
    `vi_app` and `vi_owner`;
  - support from an unbound binding fails;
  - a duplicate-origin support row fails;
  - erasure, reconcile and the retention purge work only through their functions, and
    each leaves an audit row;
  - the retention purge deletes only `people_query_audit` rows older than the period;
  - an erasure whose ledger append fails is rolled back.
- The reconcile tests behind P-103 and P-243
  (`test_polluted_reconciliation_is_dry_run_idempotent_and_preserves_raw_inputs`,
  `test_directory_company_reconciliation_is_dry_run_first_and_preserves_raw_events`) pass
  on Postgres.
- The append-only lifecycle tests for P-237, P-245 and P-248 pass on Postgres.
